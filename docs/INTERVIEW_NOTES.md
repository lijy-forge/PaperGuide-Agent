# 面试怎么讲这个项目

这份是给你照着说的。每一条分三块：

- **怎么说** —— 可以直接念出来的话，口语，不用背原文，记住意思就行
- **追问怎么接** —— 面试官大概率会问的下一句
- **要记住的数字** —— 只要记这几个，别的都能查

按推荐顺序排的。**前两条最稳，先讲这两条。**

> **面 agent 开发岗的话，换个顺序**：先讲 **十（标注复核）、十一（成本核算）、
> 十二（断点续跑）**。这三条对应的是 agent 岗最常问的三件事——你怎么知道 agent
> 是对的、跑一次多少钱、崩了怎么办。一、二两条仍然好用，作为第二梯队。

## 一、Demo 会答非所问，我第一次还修错了

> **这条最值得讲。** 它不光是个 bug，还说明你会反过来怀疑自己的修复。

### 怎么说

"我们有个离线演示模式，用一批固定的假论文，不用连网也不用 API Key，方便别人快速看效果。

但我发现一个问题：不管你问什么，它都拿那批固定论文来回答。更麻烦的是，它会把你的问题原样塞进标题和正文里。比如我问'屈服值预测'，出来的报告标题就叫《屈服值预测相关的论文》，读起来像模像样，但底下引用的全是 SLAM 的论文，一篇都不相关，而且没有任何提示。

我就加了个检查：如果问题里的关键词在语料里找不到，就在报告上标一句'这批数据和你的问题无关'。我拿 YOLO 这个词试了一下，正常出警告，我以为修好了。

结果换成中文问题再试，警告根本不出来。回头看代码才发现，我那个提取关键词的正则只认英文单词，中文问题一个词都提不出来，判断条件永远是空的，所以永远不报警。

这事儿对我触动挺大的——**我拿英文用例验证，但产品的用户是说中文的。用例跟真实用法对不上，等于白测。** 后来改成英文单词和中文词都能识别，还补了三个测试把这三种情况都锁住了。"

### 追问怎么接

**Q：那现在怎么判断问题和语料相不相关？**
"英文按单词切，中文按两个字一组去切，然后拿这些词去语料里找。一个都找不到，就说明完全不相关，直接提示'这份报告回答不了你的问题'；能找到一部分，就只提示缺的那个词。"

**Q：为什么不用分词工具？**
"因为这个判断**只需要问'有没有一个词能对上'，不需要切得准**。

两个字一组切出来的词里，肯定有一些是没意义的，但这只会让它偶尔把不相关判成相关——也就是该提示的时候没提示。它不会反过来把相关的判成不相关，不会误伤正常使用。

而引入一个分词库的代价是实打实的：多一个依赖、多一份词典。这只是演示模式的一个提示功能，不在核心链路上，我觉得不划算。

如果以后发现漏报变多，我会先加一份关键词表，而不是直接上分词。"

**Q：只报警够吗，要不要直接拒绝？**
"我考虑过。但演示模式的目的就是让人看流程长什么样，直接拒绝反而看不到东西了。所以选择照常生成、但把话说明白。"

### 要记住的数字

- 三种情况：完全不相关 / 部分不相关（比如 YOLO）/ 完全相关
- 加了 3 个回归测试

## 二、前端有 8 个测试挂了，单独跑却都能过

> 这条的亮点是：**我先猜错了一次，量了个数字才找到真因。**

### 怎么说

"前端一共 220 个测试，有 8 个挂了。奇怪的是，这 8 个分别单独跑，全都能过；合在一起跑就挂，报错是超时。

我第一反应是定时器泄漏——页面上有几个轮询的地方，会定期去问后端状态。我怀疑是这些定时器跑完没清理，越积越多把机器拖慢了。去翻代码，发现三个地方都正确清理了，这个猜测不成立。

后来我干脆加了个调试用例，把点击之后页面上发生的事全打印出来。看到两件事：一是整个页面被加了'隐藏'样式，二是页面根本没跳转过去。

原因是页面用了按需加载——不是一开始就把所有页面都下载下来，而是你点到哪个才加载哪个。加载过程中，React 会先把当前页面藏起来，显示一个'加载中'。而测试用的查找方法默认会跳过隐藏的元素，所以就找不到了。

关键是我量了一下这个加载要多久：**4.2 秒**。而测试默认只等 1 秒。等不到就报错。所以把等待时间放宽就好了。

我没有改任何业务代码。因为按需加载本身是对的，真实浏览器里加载这个是毫秒级的，4.2 秒是测试工具现场编译造成的，跟用户体验没关系。"

### 追问怎么接

**Q：直接调大超时是不是在掩盖问题？**
"要看那个慢是真慢还是假慢。如果用户真的要等 4 秒，那调超时就是掩盖。但这 4 秒是测试工具临时编译代码的开销，正常启动项目的时候这些代码是提前打包好的，加载是毫秒级。所以它是测试环境的问题，不是产品的问题。"

**Q：为什么单独跑就能过？**
"因为差不多正好卡在 5 秒这条线上。单独跑机器闲，快一点就过了；一起跑机器忙，慢一点就超。所以表现得时好时坏。"

**Q：那定时器泄漏那个猜测怎么排除的？**
"直接去看那三个 hook 的代码，确认它们在组件卸载的时候都调了清理。"

### 要记住的数字

- 220 个测试，挂 8 个
- 按需加载要 **4.2 秒**，默认只等 **1 秒**
- 改完 220 全过

### 这条你得先搞懂的概念

- **按需加载**：不是一次把所有页面都下载下来，而是点到哪个加载哪个，首屏能快一些。
- **为什么会被隐藏**：加载那一瞬间，框架先把旧页面藏起来、显示"加载中"，加载完再换上新页面。

## 三、同一套测试，我的 Mac 上全过，服务器上挂

### 怎么说

"我配了自动化测试，每次提交自动跑一遍。结果本地 800 多个测试全过，服务器上挂了。

查下来有两层。第一层是生成 PDF 需要中文字体。我的 Mac 自带中文字体，所以一直没问题；服务器是干净的 Linux，没有中文字体，直接报错。有意思的是，项目自己的 Docker 配置里早就装了这个字体包，是我写自动化配置的时候漏了。

补上字体之后还是挂。第二层更细：有个测试要检查生成的 PDF 里能不能把标题完整读出来。它是拿带空格的原标题去比对的。但 PDF 里的空格和换行，是根据字体宽度反推出来的——两边字体不一样，宽度不一样，长标题的换行位置就不一样，标题被从中间断开了，自然对不上。

改法是把空格和换行都去掉再比对。因为这个测试想验证的是'文字能完整读出来'，不是'排版一模一样'。"

### 追问怎么接

**Q：为什么不在服务器上跑 Docker，环境就完全一致了？**
"可以，而且更彻底。当时的顾虑是跑 Docker 会把每次反馈从两分钟拉到十分钟以上。折中方案是让自动化环境装和 Docker 里一样的字体包，先保证字体一致。"

**Q：这类问题怎么提前避免？**
"这次的教训很具体：**凡是依赖操作系统提供的东西，都要在代码里写清楚缺了会怎样，并且在一个干净环境里验证。**

字体就是典型——它不在依赖清单里，装不装全看这台机器。我们代码的处理其实是对的，找不到字体就直接报错，而不是悄悄换个字体生成一份乱码 PDF。问题只出在自动化环境没装。

所以两件事：一是把字体这类系统依赖和 Docker 配置对齐，别两边各写各的；二是别让'我本地能跑'成为唯一的验证途径。"

### 要记住的数字

- 本地 800 多个全过，服务器挂
- 两层原因：缺中文字体 / 字体宽度不同导致换行位置不同

## 四、有一批测试写了，但其实什么都没测

### 怎么说

"我给项目加静态检查工具的时候，它报了几个'变量定义了没用到'。本来以为是小问题，点进去一看，是测试写坏了。

举三个例子。

第一个，测试名字叫'验证两次生成结果一样'，代码里确实生成了两次，存成 first 和 second，但后面只用了 first，second 从头到尾没被比较过。最后一行还有个断言是把一个字符串替换成它自己——永远成立，等于没写。

第二个，测试名字叫'有页码的时候才显示页码'，里面取了一个变量准备当页码用，但那个变量类型就是错的，而且压根没用上。如果真用上会直接报错。所以'有页码'这个情况从来没被测过。

第三个，有两处写的是'期望抛出异常'，但没写期望哪种异常。这意味着随便抛个什么都算通过，哪怕是变量名写错导致的错误。

我把这三个都改了：补上比较、把页码那个测试重写成覆盖三种情况、把异常断言收紧到具体类型。

我的体会是——**静态检查的价值不是统一代码风格，而是它会指出那些'写了但没生效'的代码。**"

### 追问怎么接

**Q：这说明什么问题？**
"说明测试数量不等于测试覆盖。这几个测试一直是绿的，但它们保护不了任何东西。"

**Q：怎么防止再出现？**
"把静态检查加进流程，这三个就是它帮我找出来的。另外写测试的时候，断言要针对测试名字说的那件事。"

## 五、有个模块从一开始就是坏的

> **别用这条回答"最棘手的问题"。** 面试官的注意力会跑到"你交付了自己没跑过的代码"上，对你不利。可以在讲第四条的时候顺带提一句当背景。

### 怎么说（只在被追问时用）

"我梳理测试的时候发现有一批测试从来没真正跑过。原因是报告模块里有个名字没对上——一个地方引用的名字，另一个地方定义的时候少写了一段，所以整个模块导入就失败。

修复只有一行。但真正的收获是：这个模块一修好，之前导入不了的那批测试第一次跑起来，立刻暴露出十几个问题。也就是说，这一个错误把它自己的检测手段一起屏蔽掉了。"

## 六、怎么保证"有证据支撑"不是一句空话

### 怎么说

"分两块，一块是运行时拦截，一块是可以量化的评测。

**运行时拦截**是本来就有的设计。比如报告导出之前会检查：正文里出现的每一个引用编号，是不是真的能对应到参考文献列表里；模型自己在正文里写的引用编号会被**删掉重新生成**，防止它编造引用；还有演示用的假数据不允许流到正式导出，一旦发现假的网址或假的论文编号就直接报错。

这里有个挺有意思的细节：正是'删掉模型写的引用编号'这条规则，跟演示文案里手写的引用号撞上了——编号被删掉之后，句子变成了'本族包含文献 。'这样的残句。但**规则是对的，是那段文案不该自己写引用号。**

**可量化评测**是我新加的。项目原来只有一个单次运行的检查工具，能看到每个阶段成没成功，但没有固定的测试用例，也没法跨次比较。我在它上面加了一层。"

### 追问怎么接

**Q：你的评测具体测什么？**
"四条硬性规则，违反就算失败：引用编号必须能对上参考文献、每条证据必须有出处（页码或章节）和原文、对外输出不能泄漏内部编号、每篇参考文献必须有个能查到的标识比如 DOI。

另外有两个指标，是用来看趋势的，不是一票否决的。"

**Q：指标举个例子？**
"有个指标是'每段话平均引用了几篇不同的论文'。语料 5 篇的时候是 4.5，15 篇的时候是 8.9——**它跟着论文总数一起涨**，说明大部分段落是把所有论文都引了一遍，而不是只引跟这段话真正相关的那几篇。这就把'引用是凑数的'这个原来只能靠眼睛看的问题，变成了一个能设阈值、能盯着的数字。"

### 要记住的数字

- 4 条硬性规则 + 2 个趋势指标
- 那个引用指标：5 篇语料 → 4.5，15 篇 → 8.9

## 七、为什么评测要分两档，一档还必须联网

> 这条体现的是**判断力**，不是编码能力。

### 怎么说

"我把评测分成两档。

第一档跑演示模式，不用 API Key、不用联网、结果固定，一个用例一百多毫秒，所以可以每次改代码都跑。

第二档要调真实的论文检索接口。为什么非要这一档？因为**检索能不能找到论文，决定了整个流程的上限**——第一步就没搜到的论文，后面分析得再仔细、报告写得再好也补不回来。对一个做论文调研的产品，这是最该被量的环节。

但这件事在第一档里**根本测不了**。演示模式的假检索器，返回的就是那批固定语料本身。所以'搜到的'和'应该搜到的'是同一堆东西，召回率永远是 100%，等于自己考自己。这不是测得粗一点，是结构上就测不了。

好在真跑起来比我想的便宜。我本来以为得花 LLM 的钱，实际查下来检索这一步根本不需要 LLM——arXiv 的接口连 Key 都不用。而且我把规划那一步换成了固定规则的版本，这样召回率的波动就只来自检索本身，不会因为今天模型把搜索词改写得好一点就变高，数字可以跨天比。"

### 追问怎么接

**Q：真实检索的召回率跑出来是多少？**
"标注做完了 4 个用例、51 条。第一个跑出真实数字的是固体推进剂那个题目，9 条标注，
**召回率 0.33**——20 条结果里命中 3 条。

这个数字不高，但它是**第一个真数字**，而且它指向的问题很具体：漏掉的那几篇
不在 arXiv 上，是期刊论文。所以我补了 OpenAlex 这个检索源，因为它覆盖期刊。

另外三个用例还没跑出第一条基线，因为最近连检索接口一直被限流。我不打算在限流的
网络下定阈值——那样定出来的是网络状况，不是检索能力。"

**Q：没标注的时候怎么处理？**
"跳过，不算分。因为'还没标注'和'召回率是 0'是两回事，混在一起数字就没意义了。"

### 要记住的数字

- 第一档：不联网、固定结果、约 150 毫秒一个用例
- 第二档：不需要 LLM Key，arXiv 接口免费
- 第二档已有 **4 个用例、51 条标注**，跑出的第一个真实召回率是 **0.33**

## 八、架构是怎么保证不乱掉的

### 怎么说

"代码是分层的，最底下是纯粹的数据模型，上面一层层往上搭。规矩是下层不能反过来依赖上层。

但光写在文档里没用，过几个月就乱了。所以我写了个测试去查：扫描所有文件的导入语句，确认最底层那一层没有依赖上面任何模块，而且任意两个模块之间不存在互相依赖。

**写完第一次跑就挂了**——真的有两处互相依赖。不过每处只有一个方向的引用，而且只是为了写类型标注用的，不是真的要用那个功能。改成'只在检查类型时导入'就解开了，运行起来的行为没变。"

### 追问怎么接

**Q：为什么只在检查类型时导入就不算依赖了？**
"因为那种导入在程序真正运行的时候不会执行，只有做类型检查的工具会看。所以运行时的依赖方向是干净的。这本来就是解决互相依赖的常规做法，项目里两处都在用。"

## 九、任务执行怎么保证不丢

### 怎么说

"用的是 SQLite，直接写 SQL，没用 ORM。但不是拿它当个文件存数据，是当成一个任务队列在用。

几个关键点：开了并发模式让读和写不互相挡；写操作一开始就先把锁拿到，避免两边都写到一半互相等；数据库结构有版本号，升级的时候一步步迁移，而且不允许降级。

**最能说明设计思路的是死信队列**——就是那些反复失败、最后放弃的任务。逻辑是这样：每个任务被领走的时候会拿一个'租约'，相当于一个有效期。有个后台程序定期检查，如果租约还没到期，说明干活的进程还活着，不动它；如果租约过期了，说明那个进程可能崩了，就把任务放回队列重新排；但如果已经重试满三次还是不行，就移到死信表，不再重试，等人工来看。

整套逻辑是**按照'干活的进程一定会崩'来设计的**，而不是假设它一直正常。"

### 追问怎么接

**Q：为什么不用 Redis 或者专门的消息队列？**

> 别答"这个场景不需要"——面试官一定追问"为什么不需要"。要用数字说。

"因为**队列根本不是瓶颈**。

我们一个调研任务跑完要**十分钟**左右，主要时间花在调大模型和下载解析 PDF 上。执行器默认 4 个并发，也就是平均**每分钟处理 0.4 个任务**。而 SQLite 开了 WAL 模式之后，每秒能扛几千次写入。这中间差了四个数量级——队列离成为瓶颈还远得很。

而且论文分析这一层的并发是**写死上限 3** 的，配置成 4 都会被拒绝。为什么卡这么死？因为再往上加就会撞大模型的限流，还会同时下载太多 PDF 被对方封。所以**上限是大模型和对方接口给的，不是队列给的**。这种情况下换 Redis，等于去提升一个本来就不是瓶颈的环节。

反过来看用 SQLite 的好处：少部署一个服务，整个运行状态就是一个文件，拷走就能带走现场，排查问题的时候直接打开看就行。"

**Q：那什么时候你会换掉它？**

> 这个问题很可能跟着来。有答案说明你不是拍脑袋选的。

"我想过三个触发条件：

一是 **API 要跑在多台机器上**。SQLite 的锁在网络文件系统上是不可靠的，那时候必须换。

二是**真的开始抢锁**。我们设的锁等待时间是 10 秒，而且面板上有'租约过期'和'过期进程被拒绝'两个计数。如果这些数字开始往上涨，说明争抢是真的，不是我猜的。

三是**需要一份任务发给多个消费者**。现在是一个任务一个人做，如果以后要广播，SQLite 这套就不合适了。

在这之前换，就是为了没发生的问题提前付部署和运维成本。"

**Q：控制台上那几个数字是什么意思？**
"'队列长度'是已经提交但还没被领走的；'运行中'是已经被领走正在做的；'死信'是重试三次还失败、已经放弃的，正常情况一直是 0。"

> 这里有个**我自己发现但还没修的问题**：面板上"活跃工作线程"和"运行中任务"这两个数字，在代码里是**同一个计算**，所以永远一模一样。按意思讲"活跃工作线程"应该数有几个进程在干活，因为一个进程可能同时处理多个任务。**这条可以主动说出来**，显得你对自己的东西是清楚的。

## 十、我给自己的评测标注做了复核，发现四分之一是错的

> **面 agent 岗优先讲这条。** 它回答的是"你怎么知道你的评测是对的"——
> 比"我做了评测"深一层。

### 怎么说

"我给检索效果做了个评测集，就是给几个研究问题，人工标出'哪些论文必须被检索到'，
然后算召回率——该找到的找到了几篇。

标注一共 92 条候选，我按标题先判了一遍。但我不太信自己只看标题的判断，就把全部
判断结果连同判据整理出来，让另一个模型独立复核了一遍。

结果它不同意 24 条，**四分之一**。而且我核对下来它基本是对的。

更关键的是错误有两种性质。一种是判断失误：比如标题里有'joint optimization'我就纳入了，
但没分辨'联合的是什么'——有些联合的是服务缓存、有些是服务放置，跟我那个'多用户协作'
的问题不是一回事。

另一种是**代码写错了**。我筛 SLAM 论文时写的是'命中关键词后取前 15 条'，那个 `[:15]`
是按文件顺序截断，不是按相关度挑。结果同时命中两个关键词的高相关论文被位置截掉了，
而只命中一个关键词的因为排在前面被留下了。我当时跟人描述的是'按视觉语义动态这条主线挑的'
——**代码做的根本不是这件事**。

这事的价值不在于修正了标注，而在于：**如果没复核，后面所有召回数字都建立在 26% 错误的
标注上，而且错得静默**——系统检到了正确论文，标注却指向别处，永远判为漏检，你查都查不出来。"

### 追问怎么接

**Q：为什么用另一个模型复核，不自己再看一遍？**
"因为我第二遍看还是同一套判据、同一个盲点。换个独立判断才有意义。而且我给它的提示词
里明确要求逐条给结论、拿不准就说'无法判断'不要猜——猜出来的标注比没有更糟。"

**Q：它说'无法判断'的怎么办？**
"直接从标注集里去掉。标注集是尺子，留着存疑条目比少几条更糟。一共去掉了 4 条。"

**Q：那它会不会也判错？**
"会。所以我拿到结果后逐条核对了理由和标题对不对得上——比如它说第 12 条是'网络切片定价，
标题里没有任务卸载'，我去看标题确实是 `MEC Network Slicing: Slice Pricing and Resource
Allocation`，对得上。理由具体的我采纳，理由笼统的我自己再定。"

### 要记住的数字

- 92 条候选，复核不同意 **24 条（26%）**
- 拆开看：判断类 9/42，代码类 15/50
- 最终 4 个用例、51 条标注

## 十一、跑一次要多少钱，我能答上来

### 怎么说

"最开始这个项目没有任何成本统计——跑一次调研花了多少 token、哪个环节最贵，完全不知道。
这对一个天天调大模型的系统是基础设施级的缺失。

我在组装根上给 LLM 包了一层计量，**没有改任何一个调用点**。因为所有结构化调用都经过
同一个对象，包一层就全覆盖了。

现在能看到：5 篇论文的调研大概 24000 个 token，按 gpt-4o-mini 算约 0.6 美分。按调用点
拆开，**报告合成那 4 次调用占了 89%**。

这个拆解才是有用的部分——它直接告诉我该优化哪儿。要降成本，动的是合成阶段，而不是
前面的检索和阅读。"

### 追问怎么接

**Q：这是精确的 token 数吗？**

> 这个一定要主动说清楚，别等人问出来。

"不是，是本地估算。因为这个项目调大模型是走上游一个库的函数，那个函数的返回类型是
字符串——**它只把文本返回出来，响应里 provider 给的精确 token 用量就地丢掉了**。所以
进程里根本拿不到。

我是在本地用 tiktoken 按同样的编码规则自己数了一遍。对 OpenAI 的模型误差在几个百分点，
够回答'哪个阶段占大头''这次改动省了多少'，但不能当账单用。

要精确的话得改上游那个函数让它把 usage 一起返回，但那是继承来的代码，我没动。"

**Q：没配价格的模型怎么办？**
"token 照常统计，成本报'未知'而不是 0。不然'没配价格'看起来就像'免费'。"

**Q：调用失败了算钱吗？**
"不算。计量放在调用成功之后。"

### 要记住的数字

- 5 篇论文约 **24000 token**、**0.6 美分**
- **合成阶段占 89%**
- 估算误差几个百分点，不是账单

## 十二、任务跑到一半崩了，不用从头再来

### 怎么说

"这个项目用 LangGraph 做流程编排，但编译图的时候写的是 `checkpointer=None`——
**等于把 LangGraph 最主要的持久化能力关掉了**。

后果很实际：一次调研十分钟，跑到第 12 篇论文时进程崩了，前面 11 篇的大模型调用和
PDF 下载全白花，重跑要再花一遍钱和时间。

我把 checkpointer 接上了。做之前先用一个最小的三节点图验证了机制：故意让中间节点崩溃，
看断点有没有记住'第一个已完成、下一步该执行第二个'，然后续跑，确认第一个节点**没有被
重跑**。验证通过才动真正的代码。"

### 追问怎么接

**Q：接上 checkpointer 就行了吗？**

> 这里有两个坑，讲出来比"接上就好了"有说服力得多。

"不行，有两个边界决定对不对。

第一，**续跑要传 `None` 而不是状态**。LangGraph 的语义是：传状态进去等于开新的一轮，
传 None 才是从断点继续。写错了就变成每次都从头跑，看起来还'正常'。

第二，**已经跑完的线程不能续跑**。对一个已完成的线程传 None，它会把上次的最终状态直接
返回给你——**等于把一份旧报告返回给了新请求**。所以我加了个判断：只有断点存在、而且
停在中间时才续跑。

这两条我都写了测试。"

**Q：thread_id 从哪来？**
"LangGraph 需要一个 id 来定位断点，而任务本身已经有 run_id 了，直接用它。我特意没有改
图的接口签名——从状态里读出来，这样所有已有的调用点和测试里的假对象一行都不用改。"

**Q：那如果状态里没有 id 呢？**
"就不带持久化地正常跑。**编一个 id 会和别人的断点撞上**，不如不存。"

### 要记住的数字

- 原来是 `checkpointer=None`
- 一次调研约十分钟，崩了全部重来
- 两个边界：续跑传 `None`、已完成的线程不能续跑

### 这条你得先搞懂的概念

- **checkpointer**：框架在每个步骤之后把状态存下来，崩了能接着跑
- **thread_id**：一次运行的标识，用来找到它的断点

## 附二：文档里出现的词，都是什么意思

说出口的词自己得懂，不然追问一句就卡住。这些都是上面用到的：

| 词 | 大白话 |
|---|---|
| **断言** | 测试里那句"我期望结果是 XX"。不符合就算这个测试失败 |
| **回归测试** | 专门为某个已修好的 bug 写的测试，防止以后又被改坏 |
| **静态检查 / lint** | 不运行代码，光读代码就能挑毛病的工具。比如"这个变量定义了没用" |
| **正则** | 一种"按规则找字符串"的写法。我那个 bug 就是规则只写了英文字母，中文匹配不上 |
| **召回率** | 应该被找到的东西里，实际找到了多少。10 篇该搜到的搜到 7 篇，就是 70% |
| **语料** | 这里指演示模式内置的那批假论文 |
| **按需加载** | 网页不一次性全下载，点到哪个页面才加载哪个，首屏能快点 |
| **轮询** | 隔几秒去问一次后端"好了没"。（更好的做法是后端主动推送，这个项目还没做） |
| **hook** | React 里一段可复用的逻辑。这里指"定期去拉状态"那几段 |
| **组件卸载** | 页面切走、这块内容从屏幕上消失的时候。定时器要在这时候关掉，否则会一直跑 |
| **ORM** | 帮你把数据库表映射成代码对象的工具，不用自己写 SQL。这个项目**没用**，是手写 SQL |
| **SQLite** | 一个轻量数据库，整个库就是一个文件，不用单独装服务 |
| **死信队列** | 反复失败、最终放弃的任务扔的地方，等人工处理 |
| **租约** | 任务被某个进程领走时给的"有效期"。到期还没干完，就认为那个进程挂了，任务收回重派 |
| **DOI** | 论文的唯一编号，拿它能查到原文。用来证明参考文献不是编的 |
| **类型标注** | 在代码里写明"这个参数是什么类型"。只给工具和人看，程序运行时不影响 |
| **互相依赖（循环依赖）** | A 用到 B，B 又用到 A。容易出问题，也说明分层没划清楚 |
| **token** | 大模型处理文字的最小单位，计费按它算。中文一个字大约一个多 token |
| **tiktoken** | OpenAI 的分词库，能在本地按同样规则数 token，不用调接口 |
| **usage** | 模型响应里附带的"这次用了多少 token"。这个项目拿不到，所以只能本地估 |
| **checkpointer** | 框架每跑完一步就把状态存下来的东西。存了才能断点续跑 |
| **thread_id** | 一次运行的标识。续跑时靠它找到上次断在哪 |
| **标注集 / ground truth** | 人工标好的"正确答案"。算召回率得先有它 |
| **负样本** | 标注为"不该纳入"的样本。用来检查系统会不会误纳，只有正样本测不出这个 |
| **BM25** | 一个经典的文本相关度打分方法。词在这篇里出现得多、在整体里出现得少，就得分高 |

> 如果某个词你还是说不顺，**就别在回答里用它**。用自己的话绕过去，比用错术语强。

## 附三：几条提醒

1. **只讲你能把中间过程说清楚的。** 面试官追问的往往不是结论，是"你当时怎么想的"。说不清中间步骤的，宁可不提。

2. **回答技术选型时，别用"够用""不需要""场景简单"这类词收尾。** 这些是形容词，不是依据，面试官接着就会问"为什么不需要"。换成三样东西里的一样：

   - **一个数字**："任务要跑十分钟，每分钟才 0.4 个，而 SQLite 每秒能写几千次"
   - **一个约束**："并发在代码里写死上限 3，因为再高会撞大模型限流"
   - **一个触发条件**："等 API 要跑在多台机器上，我就会换"

   第三样最加分——**说明你知道现在的方案什么时候会失效**，而不是觉得它永远对。这三条随便占一条，都比"够用"强。
3. **主动说局限。** 比如"演示模式测不了检索质量"、"token 是本地估的不是账单"、"真实召回率现在只有 0.33"。自己说出来，比被问出来好，而且能自然接到"所以我下一步打算怎么做"。
4. **数字要能当场复现。** 被追问可以直接跑 `python -m evals.paperguide --tier demo`。
5. **别背原文。** 记住每条的"一句话主线"就够了：
   - 一：我修了个 bug，但用错语言的用例验证，等于没修
   - 二：先猜错一次，量出 4.2 秒对 1 秒才找到真因
   - 三：本地能跑不代表哪都能跑
   - 四：测试数量不等于测试覆盖
   - 六七：检索决定上限，而假数据测不了检索
   - 八：架构规矩要用测试守住，不能只写文档
   - 九：按"进程一定会崩"来设计
   - 十：我的标注自己复核出 26% 是错的，不复核后面所有数字都白算
   - 十一：跑一次 0.6 美分，89% 花在合成阶段——知道该优化哪儿
   - 十二：断点接上，崩了不用重新付一遍钱
